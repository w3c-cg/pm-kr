**No ship.** The memoryviews alias the same `left` and `right` bytearrays every frame. Dequeuing a packet removes it from the one-slot queue, but the sender may still be using its views while the capture thread writes the next frame into those buffers. Limiting the queue does not protect the sender’s in-flight packet.

A concrete failure is possible if `send_all(left_view)` blocks after consuming part of the view. The next `readinto(left, right)` can overwrite the buffers while the sender is still consuming them. The packet can then contain bytes from different captures despite its single sequence number and timestamp. If a packet is still queued when capture runs again, that queued packet’s views can also change. The test double copies immediately, so it does not exercise either case. The desktop test’s responsiveness is useful evidence about latency, but it does not rule out these timing-dependent corruptions.

The smallest sound correction is to give each packet exclusive ownership of its eye buffers until both sends complete. To preserve reuse and avoid per-frame copies, use a small pool of buffer pairs: capture only into a free pair, and return it after the sender finishes. With a one-packet pending queue, at least two pairs are needed for one queued packet and one in-flight packet. If the queue is full, drop the new capture or replace the queued packet while returning its pair to the pool; never overwrite a pair still queued or being sent.

A focused test should make `send_all` pause after receiving a view, capture another frame while it is paused, then resume sending. Assert that the first packet still contains exactly its original left/right frame data and that the next packet contains the next frame’s data. This directly tests buffer lifetime under the blocking behavior the transport permits.
