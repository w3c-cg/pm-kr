No-ship. The views alias the single `left`/`right` bytearrays for the lifetime of every packet; the queue limits references, not writes/ownership. Demonstrated directly from the stated semantics: if sender dequeues frame 0 and blocks in `send_all(left_view)`, capture can `readinto` frame 1 into both arrays while that send is still consuming its view, so the bytes on the wire can mix frames. Also, while a packet is still queued, next capture overwrites its views *before* `put_nowait` raises Full; the queued header remains old while payload becomes new. A quick receiver-copy test and manual responsiveness run don't exercise delayed consumption. Small safe correction: use buffer ownership from a pool; only return a pair after both eye sends finish, and drop frames when no free pair is available. To preserve one queued + one in-flight + capture writing concurrently, use at least three pairs (or otherwise enforce ownership). Simpler but slower correction: hold a lock across readinto and both blocking sends. Focused test: use a transport double that blocks before copying the left memoryview, trigger another capture while blocked, then release; assert captured payload eye tags match header sequence and each other. Also exercise pending-full overwrite by queueing one packet before sender consumes it.
