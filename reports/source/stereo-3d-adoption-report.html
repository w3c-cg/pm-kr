Stereo 3D has had established specifications for more than fifteen years: in the video codecs, the containers, the display links and the graphics APIs. The signal that says "this picture holds two views" is in millions of files and broadcasts, and every layer can read it. On Linux and on the web it was adopted only in pieces.

This report lists what exists, who reads the signal today, how the work stopped each time it was started (twice at W3C), and what a browser would need. Every claim is tied to its specification or to a public record. It is offered to the PM-KR Community Group as input for discussion.

This document is a proposal by an individual participant, Daniel Campos Ramos, offered as input to the PM-KR Community Group for its consideration. Discussion takes place on the group's public list, public-pm-kr@w3.org, and in the group's repository.

Why PM-KR cares

The group's own statement of the problem says that "knowledge on the web is flat: documents, search bars, chat windows. You can't walk through it, point at it, or explore it spatially." Knowledge3D, the group's reference implementation, represents knowledge in space. Knowledge in space reaches people only when their screens can show depth: 3D televisions and monitors, glasses, headsets and display glasses.

The uses go far beyond entertainment: molecules, anatomy and geology in science and education; terrain, circuit boards and meshes in engineering; surgery practice and training in medicine; museums and places people cannot travel to. All of them need the same thing from the platform: a way to say that a picture holds two views, and a way to show them.

The specifications that exist

Graphics OpenGL quad-buffered stereo (since OpenGL 1.0, 1992); GLX_EXT_stereo_tree; Vulkan multiview (core since Vulkan 1.1, 2018) Left and right buffers for one window; which windows have both, so a compositor can carry them; one draw for several views.
Video ITU-T H.264 Annex D, frame packing arrangement SEI (clauses D.1.25 and D.2.25 in the 2012 edition); ITU-T H.265 clauses D.2.16 and D.3.16; ITU-T H.274 clauses 8.6.1 and 8.6.2 Inside the stream: the packing (side by side, top and bottom, frame alternation and others), which view comes first, and how long it holds.

Who reads the signal today

On Linux

  • Kernel drivers. Intel's i915 has allowed HDMI stereo modes since Linux 3.13 (2013, commit 573e74adbd13), and nouveau exposes them too. The amdgpu and NVIDIA drivers did not; work for both is in progress.
  • Compositors. None upstream carries a window's two views to a stereo output. The attempts are listed in the next section.
  • Media. FFmpeg reads the SEI and exports it to players as AV_FRAME_DATA_STEREO3D. mpv detects the layout from the stream since September 2026 (PR #18490). VLC has discarded the H.264 SEI since 2017 (commit 89347c3e2d), so such video plays as flat 2D. Kodi derives its stereo mode from the stream's metadata.

On the web

  • The HTML media elements have no stereo attribute.
  • No CSS property describes stereo content: W3C's index of CSS properties lists none among its 2,279 entries (checked October 2026).
  • WebCodecs' VideoFrame carries no frame packing information.
  • Media Capabilities' only spatial field, spatialRendering, is for audio.
  • WebXR Layers has the vocabulary, but only for a headset session.
  • So a browser decodes a stereo stream and ignores its frame packing. Outside a headset, a page has no standard way to say that a video, an image or a canvas holds two views.

YouTube shows the result. Its 3D player launched in July 2009, as a Google employee's 20% project, with anaglyph, side by side and interleaved modes. Its help page still documents uploading stereoscopic 3D with st3d metadata, but the ordinary player's 3D modes are gone, with no announcement that could be found: uploads are accepted, and viewing was dropped. How the work stopped, each time

Twice at W3C

  • 2012: the Stereoscopic 3D Web Task Force of the Web and TV Interest Group (LG Electronics, KDDI and W3C staff), wiki. Its use cases were a stereo photo gallery, stereo video on demand, games, and "a web-based (HTML and CSS) user interface that is rendered in stereoscopic 3D on a 3D display". Its two requirements still hold: minimal extensions, and graceful degradation, so that the same content renders in 2D on a 2D display. Its editor's draft of 30 November 2012 proposed CSS properties (perspective-baseline, stereo-content, stereo-render-option, stereo-size-type, stereo-order-type), a 3d-display media type and a display API. It said: "Even though stereo 3D devices are widely available and the number of stereo 3D contents increases, no web standards support them yet." None of those properties entered CSS.
  • 2013: the Stereoscopic 3D Web Community Group, co-chaired from LG Electronics, with researchers of the Universitat Autònoma de Barcelona who studied how people perceive web pages converted to stereoscopic 3D: Diego González-Zúñiga, Alexey Chistyakov, Pilar Orero and Jordi Carrabina, "Breaking the Pattern: Study on Stereoscopic Web Perception" (2013), and the conversion behind its pages, Chistyakov, González-Zúñiga and Carrabina, "Bringing the Web Closer: Stereoscopic 3D Web Conversion" (2013). Its posts run from October 2013 to July 2014, its list holds three messages (2016 to 2019), and it was closed on 7 April 2023.

On the Linux desktop

  • KWin, 2014: KDE bug 335859 asked for a stereo-aware compositor. The maintainer then answered: "My system neither has that extension nor any software which uses stereo buffering." A working branch followed that December, from a developer who wrote: "Unfortunately I don't have a 3D-capable monitor, so I'm hoping that you will be able to test it." It never landed, and the bug was closed in 2023.
  • GNOME, 2014: GNOME bug 733277, quad-buffer stereo for Mutter. Its first review read: "Code looks good to me but a) I have no way of actually testing it." It was reviewed again in 2017 and closed as obsolete in 2021, never merged.
  • Wayland, 2017: a protocol and a Weston implementation with HDMI stereo modes received no review. The same author revived it in September 2026 as xx-stereoscopy-v1, now open for review.

Why it stayed niche

Nobody had to act. H.264 and H.265 define the frame packing message as supplemental, and their Annex D says so in the same words: "SEI messages are not required for constructing the luma or chroma samples by the decoding process. Conforming decoders are not required to process this information for output order conformance." A decoder that ignores the message is conformant. Each step after that was reasonable on its own:

  1. The reviewers had no stereo display, so the patches could not be tested, and they were not merged.
  2. Without support in the stack, watching 3D at home was a chore. The BBC ended its trial in 2013, finding 3D viewing "quite hassly"; ESPN closed its channel the same year, citing "limited viewer adoption"; in 2022 a well-equipped technology channel tried to play 3D files on a 3D television and said: "We gave up on trying to play 3D files."
  3. Low adoption was then read as low demand, and low demand as a reason not to review the next patch.

Together these steps form a loop. The format is niche because of the barriers, and the barriers stay because the format is niche.

The loop can be broken, and in 2026 it was, in part. The missing pieces were written and verified on real displays, and maintainers merged them: mpv, HandBrake, MKVToolNix, and Universal Media Server, whose 15.9.0 release carries the frame packing message through its transcodes. The hardware is already in homes: the 3D televisions of 2010 to 2016, the 3D Blu-ray titles still released every year, and now headsets and display glasses.

One format between programs and screens

One lesson from that work shapes everything below. Every packing a file can carry (side by side or top and bottom, full or half size, either eye first) must be read. But if every program has to handle every format for every screen, the work multiplies: every input format, times every output format, times every program that wants stereo.

So the desktop built on that work (Sparky Stereo OS, an upcoming edition of SparkyLinux; its compositor design) uses one interchange format: full side by side, left eye first, at the source's own resolution. A program decodes or renders whatever it likes inside, and hands the compositor that one format. The compositor converts it for each screen: the 3D television's own modes, anaglyph for paper glasses, one eye for an ordinary 2D screen, or a headset. Sound already works this way: programs hand the sound server plain samples at any rate, and the server sends them to HDMI, Bluetooth or a USB DAC without the program ever knowing which. Full side by side is the stereo picture's equivalent of plain samples, and it keeps both eyes in one buffer, so they always show the same instant.

What a browser would need

These are proposals for discussion, built on the 2012 task force's two requirements: minimal extensions, and graceful degradation.

  1. Read the signal. When a stream, file or manifest carries frame packing (the SEI, Matroska's StereoMode, st3d, DASH's FramePacking), expose it to the page and pass it to the platform, instead of ignoring it.
  2. Declare. Give a page one way to say that a video, an image or a canvas holds two views, reusing the vocabulary WebXR Layers already has ("stereo-left-right", "stereo-top-bottom").
  3. Deliver. Let the user agent hand the platform both views together, as one buffer with its declaration, and let the platform show them on whatever screen is attached. On a 2D screen the default is one eye, or anaglyph if the user chooses it. Nothing is forced on anyone.
  4. Keep text readable. Text and controls stay on the screen plane by default, identical in both eyes. Where depth helps, an element could declare a plane (sunk, screen or popped) and the platform would draw it for the screen: a shadow on a 2D screen, real depth on a stereo one. This revisits the 2012 perspective-baseline question, and it is the same value now being discussed for KDE's desktop styles.
  5. Ask, never switch. A media query could say that the output can show stereo (the 2012 3d-display). Switching the display into a 3D mode remains the platform's and the user's decision, never the page's.
