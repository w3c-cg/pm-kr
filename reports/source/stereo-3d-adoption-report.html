Stereo 3D has had established specifications for more than fifteen years: in the video codecs, the containers, the display links and the graphics APIs. The signal that says "this picture holds two views" is in millions of files and broadcasts, and every layer can read it. On Linux and on the web it was adopted only in pieces. HDR exposes the same architectural problem when a picture's colour description or reconstruction information is lost before it reaches the component responsible for the display. This report connects their presentation paths while distinguishing tested stereo work from the proposed HDR extension.

This report lists what exists, who reads the signal today, how the work stopped each time it was started (twice at W3C), and what a browser would need. Its application map connects established scientific and creative uses with recent stereo AI research, generated worlds and desktop interaction. Public contribution records also show how review practices and AI policies affect the path from a working implementation to upstream adoption. Every claim is tied to its specification or to a public record. It is offered to the PM-KR Community Group as input for discussion.

Why PM-KR cares

An earlier PM-KR problem statement described the desire to explore knowledge spatially rather than only through conventional document and search interfaces. Knowledge3D, an independently developed reference implementation for concepts proposed to the group, represents knowledge in space. Stereo presentation adds binocular depth to that spatial information on 3D televisions and monitors, projectors, headsets and display glasses, alongside ordinary 2D and accessible presentations.

The uses go far beyond entertainment: molecules, anatomy and geology in science and education; terrain, circuit boards and meshes in engineering; surgery practice and training in medicine; museums and places people cannot travel to. All of them need the same thing from the platform: a way to say that a picture holds two views, and a way to show them.

Applications across fields

The October 2026 outreach has helped identify a wider set of relevant workflows: creating stereo images, inspecting scientific models, designing objects, exploring generated worlds, teaching and organizing everyday work. Their relevance follows from the public work itself and can be assessed before an invitation receives an answer. This map records that relevance; participation, compatibility and adoption require their own evidence.

Who reads the signal today

On Linux

  • Kernel drivers. Intel's i915 has allowed HDMI stereo modes since Linux 3.13 (2013, commit 573e74adbd13), and nouveau exposes them too. The amdgpu and NVIDIA drivers did not; work for both is in progress.
  • Compositors. None upstream carries a window's two views to a stereo output. The attempts are listed in the next section.
  • Media. FFmpeg reads the SEI and exports it to players as AV_FRAME_DATA_STEREO3D. mpv detects the layout from the stream since September 2026 (PR #18490). VLC has discarded the H.264 SEI since 2017 (commit 89347c3e2d), so such video plays as flat 2D. Kodi derives its stereo mode from the stream's metadata.

On the web

  • The HTML media elements have no stereo attribute.
  • No CSS property describes stereo content: W3C's index of CSS properties lists none among its 2,279 entries (checked October 2026).
  • WebCodecs' VideoFrame carries no frame packing information.
  • Media Capabilities' only spatial field, spatialRendering, is for audio.
  • WebXR Layers has the vocabulary, but only for a headset session.
  • So a browser decodes a stereo stream and ignores its frame packing. Outside a headset, a page has no standard way to say that a video, an image or a canvas holds two views.

YouTube shows the result. Its 3D player launched in July 2009, as a Google employee's 20% project, with anaglyph, side by side and interleaved modes. Its help page still documents uploading stereoscopic 3D with st3d metadata, but the ordinary player's 3D modes are gone, with no announcement that could be found: uploads are accepted, and viewing was dropped. The history, with sources: stereo video on YouTube.

Pages that want stereo build it themselves. StorySplat, Sonny Cirasuolo's web viewer for Gaussian splat scenes, added a 3D View in October 2026: red-cyan glasses, side by side and top and bottom for 3D TVs and projectors, and full side by side, with its toolbar and menus drawn once in each eye at the depth of the screen, and a link parameter that opens a scene in a chosen format (its documentation). Every such page carries the per-display work alone, because it cannot tell the browser that its canvas holds two views.

How the work stopped, each time

Twice at W3C

  • 2012: the Stereoscopic 3D Web Task Force of the Web and TV Interest Group (LG Electronics, KDDI and W3C staff), wiki. Its use cases were a stereo photo gallery, stereo video on demand, games, and "a web-based (HTML and CSS) user interface that is rendered in stereoscopic 3D on a 3D display". Its two requirements still hold: minimal extensions, and graceful degradation, so that the same content renders in 2D on a 2D display. Its editor's draft of 30 November 2012 proposed CSS properties (perspective-baseline, stereo-content, stereo-render-option, stereo-size-type, stereo-order-type), a 3d-display media type and a display API. It said: "Even though stereo 3D devices are widely available and the number of stereo 3D contents increases, no web standards support them yet." None of those properties entered CSS.
  • 2013: the Stereoscopic 3D Web Community Group, co-chaired from LG Electronics, with researchers of the Universitat Autònoma de Barcelona who studied how people perceive web pages converted to stereoscopic 3D: Diego González-Zúñiga, Alexey Chistyakov, Pilar Orero and Jordi Carrabina, "Breaking the Pattern: Study on Stereoscopic Web Perception" (2013), and the conversion behind its pages, Chistyakov, González-Zúñiga and Carrabina, "Bringing the Web Closer: Stereoscopic 3D Web Conversion" (2013); González-Zúñiga's doctoral thesis, "Stereoscopic User Interfaces: Creating a Pipeline for Stereo Application Development" (2016, directed by Jordi Carrabina and Enric Martí), takes stereoscopic interfaces on the web and the desktop from sketched prototypes to the measured perceived depth. Its posts run from October 2013 to July 2014, its list holds three messages (2016 to 2019), and it was closed on 7 April 2023.

Each attempt took one of two roads. The 2012 proposal carried every 3D format into the web platform, with properties for the packing, the size and the eye order of each stereo picture, so every page, browser and screen would have had to handle all of them: the multiplication described in One presentation contract for stereo and HDR. The research that followed built something new: a tool that converts ordinary pages into stereoscopic 3D, and interfaces designed for depth. Neither reused the specifications that already carry the signal.

On the Linux desktop

  • KWin, 2014: KDE bug 335859 asked for a stereo-aware compositor. The maintainer then answered: "My system neither has that extension nor any software which uses stereo buffering." A working branch followed that December, from a developer who wrote: "Unfortunately I don't have a 3D-capable monitor, so I'm hoping that you will be able to test it." It never landed, and the bug was closed in 2023.
  • GNOME, 2014: GNOME bug 733277, quad-buffer stereo for Mutter. Its first review read: "Code looks good to me but a) I have no way of actually testing it." It was reviewed again in 2017 and closed as obsolete in 2021, never merged.
  • Wayland, 2017: a protocol and a Weston implementation with HDMI stereo modes received no review. The same author revived it in September 2026 as xx-stereoscopy-v1, now open for review.

Why adoption remained fragmented

Nobody had to act. H.264 and H.265 define the frame packing message as supplemental, and their Annex D says so in the same words: "SEI messages are not required for constructing the luma or chroma samples by the decoding process. Conforming decoders are not required to process this information for output order conformance." A decoder that ignores the message is conformant. Each step after that was reasonable on its own:

  1. The reviewers had no stereo display, so the patches could not be tested, and they were not merged.
  2. Without support in the stack, watching 3D at home was a chore. The BBC ended its trial in 2013, finding 3D viewing "quite hassly"; ESPN closed its channel the same year, citing "limited viewer adoption"; in 2022 a well-equipped technology channel tried to play 3D files on a 3D television and said: "We gave up on trying to play 3D files."
  3. Low adoption was then read as low demand, and low demand as a reason not to review the next patch.

Together these steps can reinforce a loop: fragmented support makes use difficult, and limited adoption weakens the incentive to complete the support. The application map shows why the scope of useful workflows is broader than the audience of any one application or display format. The size of that audience and the benefit in each workflow still need measurement.

The loop can be broken, and in 2026 it was, in part. The missing pieces were written and verified on real displays, and maintainers merged them: mpv, HandBrake, MKVToolNix, and Universal Media Server, whose 15.9.0 release carries the frame packing message through its transcodes; then Qt Multimedia, which reports the layout to every Qt player, Bino, which now shows right-eye-first videos the right way round, and PeerTube, which keeps the packing when it transcodes an upload (October 2026). The hardware is already in homes: the 3D televisions of 2010 to 2016, the 3D Blu-ray titles still released every year, and now headsets and display glasses.

Upstream adoption and contribution practices

The 13 October 2026 Media and Entertainment Interest Group discussion raised both AI-related resistance to contributions and the need for a migration path from the current stack. The cases below make those questions concrete: they concern contributions to media software and a display driver, whose projects have different review practices and policies. These are public records from the report author's own contribution campaign, not an independent survey of acceptance rates.

The Linux kernel discussion in context

The relevant public chronology places nouveau's decision alongside the broader kernel discussion. All dates are in 2026.

  1. 14 July: Linus Torvalds states that Linux is not an anti-AI project. His 21 August Xe driver fix subsequently credits AI-assisted debugging under his direction.
  2. 2 October: the report author argues in nouveau's policy discussion for engineering responsibility, reproducible tests, reviewable changes and language access, using established engineering tools as an analogy.
  3. 8–9 October: the Maintainers Summit reaches consensus to deprecate compulsory Assisted-by tagging. Sasha Levin's 9 October removal proposal records that consensus.
  4. 9 October: following nouveau's policy merge, the author writes to its public list about judging understanding and responsibility, and respecting the restriction by maintaining the work downstream.
  5. 13 October: Torvalds opposes tool-based restrictions, using compilers and editors as analogies and emphasizing the contributor's understanding of the work.

This records parallel public arguments, without establishing influence between their authors. The 9 October nouveau email preceded Torvalds's 13 October reply, but followed the summit consensus and the removal proposal. A kernel-wide discussion also does not by itself establish a change to nouveau's contribution rules.

Making project conventions usable by humans and AI

The MKVToolNix alignment exchange gives a small, concrete example of translating a maintainer's expectations into an actionable procedure. The author reports explaining to the AI collaborator why the requested spacing mattered to visual grouping in the editor; the public thread records the requested alignment and the resulting revisions. That human explanation connected the purpose of the convention to the change being made.

Projects could express such knowledge in versioned contributor documentation and skill files: scope and rationale, before-and-after examples, local naming and layout rules, test commands, disclosure requirements, and the decisions that remain with maintainers. Formatters and linters can enforce mechanical rules; examples and explanations can guide context-dependent decisions. AI assistance can then help adapt a contribution to each project's conventions while the contributor checks the result and answers review. Existing restrictions still apply unless the project changes them.

This is a concrete PM-KR use case: preserving a rule's meaning, procedure, authority and revision so a human and an AI client can work from the same knowledge. It connects to Knowledge3D's Dual-Client Contract and Knowledge Proceduralizer as a proposed exchange experiment, detailed in the transition report. The cases motivate testing whether explicit shared guidance reduces repeated review corrections; they do not yet measure that benefit or establish AI as the easiest approach for every project.

One presentation contract for stereo and HDR

One lesson from that work shapes everything below. Every packing a file can carry (side by side or top and bottom, full or half size, either eye first) must be read. But if every program has to handle every format for every screen, the work multiplies: every input format, times every output format, times every program that wants stereo.

So the desktop built on that work (Sparky Stereo OS, an upcoming edition of SparkyLinux; its compositor design) uses one interchange format: full side by side, left eye first, at the source's own resolution. A program decodes or renders whatever it likes inside, and hands the compositor that one format. The compositor converts it for each screen: the 3D television's own modes, anaglyph for paper glasses, one eye for an ordinary 2D screen, or a headset.

Sound already uses this division: programs hand the sound server PCM samples with their rate and channel layout, and the server adapts them for the selected output. Decoded picture samples, with their stereo layout and colour description, are the visual equivalent. Full side by side keeps both views associated with the same presentation frame in one buffer; preserving HDR precision, luminance information and any gain map would let the compositor adapt that picture to each display. The same principle serves stereo and HDR: describe each content layer once, preserve its information through the stack, and convert for the screen at the output.

Stereo layout and colour are independent properties of that contract: an HDR picture can have one view or two, and a stereo picture can be SDR or HDR. Colour needs an explicit description, such as the primaries, transfer characteristics, matrix and range exposed by WebCodecs. Gain-map images also carry reconstruction information whose use depends on the display's available headroom. The proposed stereo and HDR declaration keeps that information associated with each content layer, so SDR controls can accompany HDR pictures and each output can make its own presentation decision.

HDR: a shared principle, an engineering choice still to test

PQ, HLG and gain-map images present different decoding and reconstruction requirements; they are not interchangeable labels for one encoding. Full side by side settles where the stereo views go, but does not settle HDR's pixel representation, working colour space, precision or metadata transport. The author selected the stereo interchange after testing content and devices; comparable cross-format HDR device testing has not yet been done for this proposal. Its HDR conclusions are based on specifications and architectural reasoning, not an equivalent measured implementation.

A floating-point working representation and compositor-side gain-map reconstruction are design candidates. Before selecting and claiming an HDR interchange, the work needs reference images and measurements across PQ, HLG and gain-map sources, mixed SDR/HDR content, and HDR, deep-colour SDR and 8-bit outputs, including mirrored screens. Evaluation must cover colour and luminance, clipping and banding, metadata lifetime and the two eyes' consistency. Deep colour alone is not HDR, and the existing stereo and deep-colour tests do not validate this HDR path. Dynamic HDR metadata remains outside the first proposed implementation.

What a browser would need

These are proposals for discussion, built on the 2012 task force's two requirements: minimal extensions, and graceful degradation.

  1. Read the signal. When a stream, file or manifest carries frame packing (the SEI, Matroska's StereoMode, st3d, DASH's FramePacking), expose it to the page and pass it to the platform, instead of ignoring it. Preserve the colour description and applicable HDR reconstruction information alongside the picture.
  2. Declare. Give a page one way to describe each video's, image's or canvas's stereo layout and colour properties, reusing the vocabulary WebXR Layers already has ("stereo-left-right", "stereo-top-bottom") and existing colour descriptions.
  3. Deliver. Let the user agent hand the platform both stereo views together, as one buffer with its declaration, and let the platform show them on whatever screen is attached. On a 2D screen the default is one eye, or anaglyph if the user chooses it. The HDR extension would preserve precision and reconstruction information until adaptation for each output, subject to the engineering evaluation above.
  4. Keep text readable. Text and controls stay on the screen plane by default, identical in both eyes. Where depth helps, an element could declare a plane (sunk, screen or popped) and the platform would draw it for the screen: a shadow on a 2D screen, real depth on a stereo one. This revisits the 2012 perspective-baseline question, and it is the same value now being discussed for KDE's desktop styles.
  5. Ask, never switch. A media query could say that the output can show stereo (the 2012 3d-display), alongside existing HDR capability queries. Switching display modes remains the platform's and the user's decision, never the page's.
